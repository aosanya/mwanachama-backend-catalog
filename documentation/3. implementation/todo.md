| CAT8 | 🃏 **A listing cannot carry the card — declared document projections.** | 📋 | Found 2026-09-23 wiring the website onto this module (W15), and it blocks that row's second half. `ListEntries` strips `Doc` unconditionally, for a good reason its own comment gives: carrying it would put 34 KB per row into every index page. But the storefront's card is not just slug/name/summary — it needs `sector` and the enabled `modules`, and both live **inside** the document. The SQL this module replaced computed them in the database: `list_public_agencies` returns `sector` as a column and folds `doc -> 'modules'` down to the enabled codes with `jsonb_agg`. Neither is decorative — `sector` drives the whole filter dropdown on `/agencies` and appears on every card, and `modules` renders as the chips beneath it. So today the website can filter *by* a document path (`ListFilter.Docs` already does that) but cannot *read* one back without fetching whole documents one at a time. The shape that fits this module rather than fighting it: the spec already declares which document paths are worth indexing, so let it also declare which ones a listing carries — a projection, keyed by path, returned as declared values beside the card. The module still never learns the word "sector"; it learns "these declared paths come back in a listing", which is the same trick `Index.Path` already plays. Two things to decide: whether a projection may name a non-scalar path (`modules` is an array of objects, and the fold that selects the enabled ones is real logic, so the honest first answer is that the array comes back whole and the caller folds it), and whether projections belong on the object or on the request, since an operator listing and a public one may want different ones. Until it exists, a caller wanting a card either fetches every document or keeps a second read path in SQL — which is exactly the duplication this module was built to end. |

| CAT15 | 🧱 **A domain register wants typed, queryable records — this module offers an opaque document with a review state.** | 📋 | Filed 2026-09-28, from the owner's direction that collected data should land in a store of its own the way a posting lands in accounting's ledger, met concretely while building the `party-mobilization` agency template (its `catalog.json` carries this as four sized `unenforceable` entries; the other half is `mwanachama-backend-forms`' F5, and the two are one design). Being domain-free is exactly what makes this module the right host — "a word that means something in one domain and nothing in another does not belong in this module" is why `Entry` can hold records it does not understand. Two things are missing before it can be a register rather than a library. **(1) No declared record type.** `models.Entry` is `{ID, Slug, Name, Summary, Doc, Visibility, SubmittedBy, ApprovedAt, …}` with `Doc` a plain string, so a `SentimentRecord` is JSON in a text column with no shape the module enforces on the way in. The seam already exists and is this module's own idiom: the spec declares enum values and `validate.go` checks them at the write, deliberately rather than as a database CHECK — a declared record type per catalog is the same discipline applied to `Doc`. **(2) No query into `Doc`.** Reads are by slug, document path and visibility; "which wards moved between round 2 and round 3" is not a question this module can answer, which is the whole point of landing records here rather than leaving them in forms. Needs indexed JSON-path filters on `Doc`, or typed columns per record type — and it overlaps CAT8's declared document projections, which is the same problem read-side only, so plan them together. Two smaller gaps in the same area: visibility is per `Entry`, so a ward aggregate and the identified responses behind it cannot be one object with two audiences; and `Entry` has `Deleted` but no scheduled transformation, so a retention rule like "drop identified detail to ward level after the cycle" is policy a person executes. |

| CAT19 | 🐞 **SECURITY — a mining run reporting failed builds undoes a reviewer's reject and never reaches the stall: a failed-attempt report racing `decide rejected` puts the suggestion back to `approved`, and concurrent failures lose their count so the tenth never stalls it.** | 📋 | P2 — two of CLAUDE.md's "Behaviours to preserve" ("The tenth failed build stalls a suggestion"; a reviewer's decision standing) unenforced under concurrency, reachable by any holder of `catalog.suggestion.record_attempt`. **Did**: on the package's own manager over a local Postgres 16 (2026-09-30, master 7b07a1c, the shipped `agency.catalog.json`): 200 fresh suggestions, each approved, then at once `DecideSuggestion(id, rejected, 0)` beside `RecordSuggestionAttempt(id, "run1", "failed")`; then 20 fresh approved suggestions, each given twelve concurrent `RecordSuggestionAttempt` calls. **Observed**: both calls return `nil`, yet **47/200** suggestions read `approved` afterwards — the reject is gone; after twelve concurrent failures every one of the 20 reads `approved` with `attempts` of 2 to 4 and twelve run comments (numbered from those same stale counts) — **20/20 never stalled**. **Cause**: `RecordSuggestionAttempt` (`suggestion.go`) reads the row, computes `attempts := existing.Attempts + 1` and `status := existing.Status`, and writes both with `where id = ?` only — so it writes back the `approved` it read over a reject that committed in between, and concurrent reports each write the same incremented count. **Threat**: the stall is the cost ceiling on the miner (ten builds, then a human must re-approve); a run that reports its failures in parallel builds without limit, and a reviewer's reject can be silently reversed by an in-flight report, sending the miner back to an archetype the reviewer turned down. Reachable only by holders of the run's action, and it overrides a decision rather than disclosing content — hence P2. **Control**: make the write conditional — `attempts = attempts + 1` in SQL, or `where id = ? and status = 'approved' and attempts = ?` treating zero rows as `ErrSuggestionStatus` — so a report counts only against a suggestion still approved when it is written. **Verdict**: open. Red test: `suggestion_attempt_race_security_test.go`'s `TestCAT19_OpenHole_FailedAttemptReportRevivesARejectedSuggestion` — runs `DecideSuggestion(rejected)` between the report's read and its write and today prints `CAT19 (P2) open hole: a reviewer rejected suggestion clinic while a failed-attempt report was in flight, the reject succeeded and the report answered <nil>, and the suggestion now reads "approved" with 1 attempts; want it to stay rejected…`; the conditional write above turns it green (checked, reverted).
