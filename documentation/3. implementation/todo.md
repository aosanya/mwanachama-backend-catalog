| CAT8 | 🃏 **A listing cannot carry the card — declared document projections.** | 📋 | Found 2026-09-23 wiring the website onto this module (W15), and it blocks that row's second half. `ListEntries` strips `Doc` unconditionally, for a good reason its own comment gives: carrying it would put 34 KB per row into every index page. But the storefront's card is not just slug/name/summary — it needs `sector` and the enabled `modules`, and both live **inside** the document. The SQL this module replaced computed them in the database: `list_public_agencies` returns `sector` as a column and folds `doc -> 'modules'` down to the enabled codes with `jsonb_agg`. Neither is decorative — `sector` drives the whole filter dropdown on `/agencies` and appears on every card, and `modules` renders as the chips beneath it. So today the website can filter *by* a document path (`ListFilter.Docs` already does that) but cannot *read* one back without fetching whole documents one at a time. The shape that fits this module rather than fighting it: the spec already declares which document paths are worth indexing, so let it also declare which ones a listing carries — a projection, keyed by path, returned as declared values beside the card. The module still never learns the word "sector"; it learns "these declared paths come back in a listing", which is the same trick `Index.Path` already plays. Two things to decide: whether a projection may name a non-scalar path (`modules` is an array of objects, and the fold that selects the enabled ones is real logic, so the honest first answer is that the array comes back whole and the caller folds it), and whether projections belong on the object or on the request, since an operator listing and a public one may want different ones. Until it exists, a caller wanting a card either fetches every document or keeps a second read path in SQL — which is exactly the duplication this module was built to end. |

| CAT11 | 🐞 **BUG — a soft-deleted Entry's slug can never be reused, although every read reports the slug as free.** `Entry.slug` is declared `unique: true` as a plain column-level constraint in `catalog.blueprint.json` — a whole-table unique index with no `where deleted = false` — while `DeleteEntry` only ever sets `deleted = true`; the row, and its slug, stay in the table forever. `findEntry` (and so `GetEntry`/`OpenEntry`/`UpsertEntry`'s create-fallback) filters `deleted = false`, so every read of that slug says `ErrEntryNotFound`, but `CreateEntry`'s `m.insert` hits the surviving unique constraint and returns `ErrEntryExists`. Demonstrated against a real `CatalogManager` (sqlite, the shipped `agency.catalog.json` spec): created `squatted`, deleted it, then `GetEntry`/`OpenEntry` both returned `entry not found`, and `CreateEntry`/`UpsertEntry` on the same slug both returned `entry slug already in use` — real output: `PROBE GetEntry after delete: entry not found` / `PROBE re-CreateEntry same slug after delete: {...} entry slug already in use`. A caller who deletes an Entry (or who deletes-then-reimports the same domain object) loses that slug permanently, with no error at delete time warning them, and no way to free it — this is the same class of "the module says it's gone but the database still holds it against you" as CAT2's byte-vs-canonical bug, just on the identity column rather than the document. **`mwanachama-backend-shared/spec` already has the fix's building block**: `Index.Unique` + `Index.NotDeleted` together already emit `create unique index ... where deleted = false` (`migrate.go`'s `createIndexes`) — nothing new needed there. **Fix location**: `catalog.blueprint.json`'s `entry.slug` field should drop its column-level `"unique": true` and gain a matching partial-unique index (`fields: ["slug"], unique: true, notDeleted: true`) on the `entry` object instead — a blueprint-only change, so every domain gets it at once. Pinned rather than only described: `TestCAT11_PinsKnownDefect_DeletedSlugCanNeverBeReused` (`entry_test.go`) asserts today's `ErrEntryExists` on both `CreateEntry` and `UpsertEntry` after a delete; it must go red (both calls returning `nil`) once the blueprint fix lands. | 📋 | Found 2026-09-27 by the scheduled integration-test sweep, probe-first against a real `CatalogManager` — no product code touched, the demonstrating `zz_probe_delete_test.go` was deleted after capturing the output quoted above. `go test ./...` and `go test -tags=integration ./...` both clean with the pinning test in place. |
