| CAT8 | 🃏 **A listing cannot carry the card — declared document projections.** | 📋 | Found 2026-09-23 wiring the website onto this module (W15), and it blocks that row's second half. `ListEntries` strips `Doc` unconditionally, for a good reason its own comment gives: carrying it would put 34 KB per row into every index page. But the storefront's card is not just slug/name/summary — it needs `sector` and the enabled `modules`, and both live **inside** the document. The SQL this module replaced computed them in the database: `list_public_agencies` returns `sector` as a column and folds `doc -> 'modules'` down to the enabled codes with `jsonb_agg`. Neither is decorative — `sector` drives the whole filter dropdown on `/agencies` and appears on every card, and `modules` renders as the chips beneath it. So today the website can filter *by* a document path (`ListFilter.Docs` already does that) but cannot *read* one back without fetching whole documents one at a time. The shape that fits this module rather than fighting it: the spec already declares which document paths are worth indexing, so let it also declare which ones a listing carries — a projection, keyed by path, returned as declared values beside the card. The module still never learns the word "sector"; it learns "these declared paths come back in a listing", which is the same trick `Index.Path` already plays. Two things to decide: whether a projection may name a non-scalar path (`modules` is an array of objects, and the fold that selects the enabled ones is real logic, so the honest first answer is that the array comes back whole and the caller folds it), and whether projections belong on the object or on the request, since an operator listing and a public one may want different ones. Until it exists, a caller wanting a card either fetches every document or keeps a second read path in SQL — which is exactly the duplication this module was built to end. |
